## Verified result

Full replay `build-release/vif-capture-2488m.txt` reaches 248,800,000 steps and
saves a 3,936-byte stream to `build-release/first-vif.bin`. Its framebuffer remains
hash `3F7CE0BA02868615`, with 122 RGB pixels. This replay includes the September 6
scissor fix. Standalone replay of that stream takes approximately 0.040 seconds
on this host and reproduces 998 VU pairs, 8 queued/1 rejected path-1 tags, five
triangles, rejection PC 0x00C0, kick start 0x0120, bad tag address 0x0160 and tag
`00000000420F028B`. This is a debugging turnaround measurement, not Vita speed.

The standalone GS image is NOT equivalent to the full BIOS image: earlier path-3
register/texture state is absent. The VU rejection agrees despite that limitation.

## Source bytes resolve the VIF-copy question

The first VIF UNPACK is code `6C168000` at stream byte offset 0x073C, immediately
after STCYCL `01000404`. It uploads 22 vectors to TOPS-relative qword zero,
then MSCAL `14000000` occurs at 0x08A0. The source payload already contains:

| VU qword | Four source words |
| --- | --- |
| 0x12 | 00000002 10000000 0000000E 00000000 |
| 0x13 | 00000000 00000000 00000000 00000000 |
| 0x14 | 00000000 00000000 00000000 00000000 |
| 0x15 | 00000000 00000000 00000000 00000000 |

Thus VIF's copy did not erase the two A+D entries or the expected terminating
tag. This does not establish whether the guest intended these values: investigate
EE packet construction or DMA stream assembly upstream. Do not patch in EOP.
The first upload stops at qword 0x15; data encountered beyond that is not part
of that initial UNPACK payload. Avoid attributing it to the upload without tracing
intervening VU stores. Later stream commands set BASE/OFFSET and alternate six
17-vector UNPACK/MSCNT submissions.

Next: use the saved 3,936-byte replay for VIF/VU hypotheses, and trace the EE
writes/DMA source that produced stream qwords 0x12..0x15. Retain full BIOS replay
as the integration check. No new visible intro or audio milestone is claimed.

## DMA source mapping and EE writers

The last successfully assembled VIF DMA chain now retains bounded source-span
metadata alongside the actual copy. Tests cover TTE/inline boundaries, referenced
payload without TTE, and reset. Full replay `vif-source-2488m.txt` maps stream
offset 1856 (0x740) to EE address 0x002740E0. Therefore qwords 0x12..0x15 originate
at 0x00274200..0x0027423F. The first VIF DMA starts at EE PC 0x0021D6B4,
step 248772997, from TADR 0x00273990. Hash and RGB count remain unchanged.

A narrow, BIOS-specific host trace of attempted GPR stores and SWC1 stores to
that 64-byte range (`vif-writers-2488m.txt`) shows initial SQ clearing at PC
0x8000E5E8, followed by byte stores at PCs 0x00100BD0/0x00100BEC/0x00100C04.
Those stores reproduce the header bytes and explicitly write zero payloads.
The trace is not a universal bus-write observer: it records instruction attempts,
not fault/commit status or DMA writes. Its values agree with the captured stream.

Important change in interpretation: the primary PCSX2 source contains an explicit
BIOS note at the path-1 size guard in
[GetGSPacketSize](https://github.com/PCSX2/pcsx2/blob/master/pcsx2/Gif_Unit.h).
It describes the BIOS exceeding VU memory size and sensitivity to XGKICK timing.
[VUops](https://github.com/PCSX2/pcsx2/blob/master/pcsx2/VUops.cpp) transfers
incrementally, unlike our immediate snapshot. This is supporting evidence for a
timing limitation, NOT proof that this exact packet is identical or that a fixed
delay is correct. No artificial EOP, larger cap, or BIOS-specific delay was added.
Do not label this rejection a proven intro blocker or these bytes corruption.
