## Dual-core SPU2 DMA checkpoint

The preserved SPU2 experiment initially regressed the retail BIOS from the
verified 434 SIF0 activity transitions to 20. A stop at the first stalled poll
showed that the BIOS initializes and starts both SPU2 DMA paths together:

- DMA4/core 0: MADR `0x0004FA00`, BCR `0x00300010`, CHCR `0x01000201`;
- DMA7/core 1: MADR `0x0004FA00`, BCR `0x00300010`, CHCR `0x01000201`.

The core-0 server then polls SPU2 status `0x1F9001B0` and DMA4 MADR
`0x1F8010C0`. Persistent SPU2 register readback exposed this real wait, but the
experiment modeled only DMA7, so DMA4 never advanced and the IOP remained in
the poll loop.

The timed SPU2 transfer model now covers DMA4 and DMA7. Each core keeps
independent source, TSA, byte-count, and deadline state; completion copies the
IOP payload into sound RAM, advances MADR and TSA, clears BCR/CHCR start, sets
the appropriate DICR status bit (DMA4 bit 28 or DMA7/DICR2 bit 24), and raises
the shared IOP DMA interrupt line. Focused tests cover both channels.

The 200-million-step retail replay recovers exactly 434 SIF0 activity
transitions with both processors still running. Extending the replay to 250
million steps remains instruction-valid but does not increase the SIF0 count or
start post-initialization VIF/GIF DMA. The final sampled state is EE PC
`0x00081FDC`, IOP PC `0x000974F8`, with 34 stores to the traced RPC wait-state
range. This is a correctness checkpoint, not a visible-graphics claim.

## Optimization-plan alignment

The coworker-provided unconventional optimization plan was reviewed in full.
Its central recommendation is compatible with the current architecture: retain
the exact interpreter as oracle/fallback, but make the PC side profile-guided
and remove emulator-shaped work through guarded traces, width-aware AstraIR,
event horizons, and certified polling-loop collapse.

The next major optimization milestone should therefore be the plan's Phase A:
emit a compact, versioned, machine-readable execution census from a 200-million
step BIOS run without changing architectural behavior. Initial fields should
cover EE/IOP block and edge counts, indirect targets, event spacing, MMIO poll
sites, and DMA sizes. The observed SPU2 DMA4 polling loop is a useful report-only
`WAIT_DMA_COMPLETE` candidate; acceleration must wait for explicit timing,
guard, and fallback contracts. After the census is stable, introduce a minimal
AstraIR for the already-supported AOT subset rather than expanding a monolithic
emitter.

## Execution Census phase A1

The first census schema is now implemented. A reusable dynamic collector records
retired-instruction block entries and edges for either MIPS processor, including
normal delay slots, annulled branch-likely slots, indirect transfers, and
interrupt/exception discontinuities. `ps2bios_trace` accepts an optional final
path and writes deterministically sorted schema-version-1 JSON for both EE and
IOP.

The 200-million-step 02.00E capture produced a 1,063,094-byte profile:

- EE: 199,999,907 retired instructions, 2,460 block PCs, 3,132 edges;
- IOP: 24,999,461 retired instructions, 5,006 block PCs, 6,896 edges.

Enabling collection preserves the established 434 SIF0 transitions and the
same final sampled endpoints: EE `0x00081FDC`, IOP `0x000974F8`. Focused tests
cover deterministic block/edge counts and an annulled branch-likely delay slot.
The next census increment is indirect-target and `$sp`/`$gp` observation, not a
runtime optimization.

The census collector is host-only and is not linked into the Vita runtime. The
post-census VitaSDK cross-build succeeds; `build-vita/ps2vita.vpk` SHA-256 is
`81D0B526A93AF6A5A3A160DCEC1EF87FC47AAB8A32461C21428F090408FA82A9`.

## Execution Census phase A2

Schema version 2 adds the next profiling inputs requested by the optimization
plan: unsigned `$sp`/`$gp` ranges at each block entry and observed `JR`/`JALR`
targets. Indirect targets are accepted only when the next retired block matches
the source-register value captured at the branch, so an interrupt after the
delay slot is not classified as a target.

The version-2 200-million-step capture remains instruction-valid at the same EE
and IOP endpoints and preserves 434 SIF0 transitions. Its 1,977,350-byte JSON
contains:

- EE: 355 indirect sites and 710 site/target pairs; 242 sites are monomorphic;
- IOP: 765 indirect sites and 2,022 site/target pairs; 528 sites are monomorphic;
- stable `$gp` at 2,044 of 2,460 EE block PCs and 3,633 of 5,006 IOP block PCs;
- stable `$sp` at 1,909 EE block PCs and 2,811 IOP block PCs.

These are profile observations, not hardcoded assumptions. Future trace and
memory specialization must turn them into explicit guards with exact fallback.

## Execution Census phase A3

Schema version 3 records retired EE/IOP MMIO loads by instruction site, physical
address, access width, and count. It also aggregates spacing in EE master steps
for observed SIF0, interrupt, graphics/SIF1 DMA, and SPU2 DMA edges. These event
statistics describe observed history; they are not yet a proof that a compiled
trace can run until a particular future cycle.

The deterministic 200-million-step capture again preserves 434 SIF0 transitions
and the same CPU endpoints. Its 2,019,292-byte JSON reports:

- 172 EE MMIO site/address pairs and 2,297,997 total reads;
- 345 IOP MMIO pairs and 355,171 total reads;
- 217 SIF0 starts and completions, matching the existing transition count;
- 79 EE and 540 IOP interrupt rising edges;
- 86 SIF1 DMA starts, one SPU2 DMA4 start, and two SPU2 DMA7 starts;
- no observed VIF0, VIF1, or GIF DMA start after initialization.

Most importantly, IOP `0x00097500` reads SPU2 `0x1F900744` 222,884 times and
ends adjacent to the final sampled PC `0x000974F8`. This newly measured late
SPU2 poll is a much stronger next correctness and eventual `WAIT_MMIO` research
candidate than the earlier DMA4 poll, which executes about 994 reads in this
capture. It must be decoded and modeled before any wait-loop acceleration is
attempted.

## SPU2 STATX readiness checkpoint

The Phase A3 census turned its hottest late IOP MMIO pair into a concrete
correctness fix. `0x1F900744` is SPU2 core 1 `STATX`; BIOS instructions at
`0x000974D0..0x000974DC` read the register, mask ready bit `0x0080`, and leave
the routine when it becomes nonzero. Because the previous passive register
array reset to zero and DMA never updated STATX, the BIOS instead exhausted a
`1 << 24` iteration timeout ending at `0x000974F8`.

Both cores now reset with STATX ready. Starting DMA4 or DMA7 clears ready and
sets busy bit `0x0400`; timed completion clears busy and restores ready while
the core remains in DMA mode. Focused tests cover reset, active, and completion
states on both channels, and the full host test suite passes.

The corrected 200-million-step census demonstrates forward progress:

- SIF0 activity transitions increase from 434 to 452;
- the status-timeout site drops from 222,884 reads to zero and total IOP MMIO
  reads fall from 355,171 to 140,236;
- IOP coverage grows from 5,006 to 5,016 blocks and 6,896 to 6,922 edges;
- SIF1 starts increase from 86 to 95 and DMA7 starts from two to five;
- the final IOP sample moves from `0x000974F8` to `0x00093F10`.

The EE remains running at `0x00081FC0`. No VIF0, VIF1, or GIF DMA start is yet
observed, so the result is a stronger boot/device baseline but not a claim of
graphics output.

## Minimal AstraIR checkpoint

through typed AstraIR instruction records before C++ emission. The new
`tools/astrair/ir.py` defines operation and operand records, while
`tools/astrair/builder.py` owns decoding for only the previously supported

## AstraIR effects and barriers checkpoint

Following the plan's Commit 5, AstraIR instructions now carry explicit,
conservative architectural effect masks. Arithmetic and packed-bitwise nodes
are pure. Loads may read memory, fault, or touch MMIO. Stores may write memory,
fault, touch MMIO, or schedule an earlier device event. The corresponding hard
barrier predicate prevents future multi-block traces from crossing those
operations until address provenance proves a safer classification.

Effect tests cover pure, load, and store nodes. Generated Phase-0 C++ remains
byte-identical at the established SHA-256, both host tests pass, and the VitaSDK
cross-build succeeds. CMake now disables Python bytecode output for generator
and IR tests so verification leaves no source-tree cache artifacts.

## AstraIR scalar width checkpoint

Following Commit 6 of the plan, AstraIR now records result width and upper-bit
knowledge for the supported subset and performs conservative straight-line
propagation. The analysis recognizes boolean and 16-bit-zero results,
32-bit-sign-extended scalar results, 64-bit values, and packed 128-bit values.
It safely refines common `LUI -> ORI`, `$zero`-based `ORI`, and masked `AND`
chains while leaving unknown inputs wide.

The generator now consumes the refined IR records, but emission deliberately
does not use the facts for optimization yet. Width tests and the full execution
oracle pass, and generated C++ remains byte-identical at the established hash.

## AstraIR liveness foundation

The first half of the plan's Commit 7 now computes exact low-GPR use/def sets
and backward `live_in`/`live_out` facts for straight-line IR. Tests cover a
write overwritten before use, a later value consumed by a live result, and
store dependencies on both base and value registers. Register zero never
appears as a live mutable value.

No writeback is removed in this checkpoint. Generated C++ remains byte-identical
and all execution oracles pass. Deferred state materialization will follow
behind a generator switch and must flush on every direct, indirect, stop,
memory-fault, and interpreter exit.

## Deferred GPR writeback checkpoint

The second half of Commit 7 now caches referenced nonzero low GPRs within each
generated function and flushes dirty locals immediately before every existing
architectural commit path. The implementation is generator-flagged through
`ASTRART_DEFER_GPR_WRITEBACK`; disabling it regenerates the exact legacy source
hash. Packed high halves and HI/LO remain conservative direct state updates.

Both modes pass the full differential suite. A new host Release CLI benchmark
runs the existing checksum-validated workload with a real monotonic clock. At
20,000 iterations and nine median samples, three independent optimized runs
reported 160.304, 160.148, and 163.610 ms; legacy runs reported 164.640,
162.130, and 161.282 ms. The median-of-run medians improves about 1.1%. This is
useful keep/discard evidence on x86, but no physical-Vita speedup is claimed.
