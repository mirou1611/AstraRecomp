# Session 2026-09-24: VU1/VIF execution-path optimization

The first captured BIOS VIF1 packet is the local performance and correctness
workload. It still executes 998 VU pairs in 1308 modeled cycles, ending at
micro-PC 0x0308. A separately built pre-optimization commit (`2197b90`) and
the optimized core produce the same VU-register/data/counter checksum
`B914A64CD3201B71` and the same delivered GIF-byte/rejected-tag checksum
`19964F619C2D7AC8`. This is not a new intro frame or a fix for its suppressed
geometry.

## Changes

- Replace the 31-register-by-four-lane readiness scan with the up-to-two
  vector sources actually read by each instruction. Preserve per-lane hazards.
- Snapshot only the lower instruction's VF sources before upper execution,
  retaining the same-pair read-before-write behavior and VF0 source value.
- Add aligned VU1-local micro/data word and data-qword accessors. VU1 no longer
  routes every local fetch/load/store/GIF transfer through the EE bus decoder
  and TLB. VIF1 MPG/UNPACK uploads use the same local banks while preserving
  its causal/provenance records.
- Add `ps2vu_benchmark` and bank-edge/coherence unit checks. Whole-packet mode
  checks VU state and delivered GIF packets after every repetition; VU-only
  mode checks the first, every 64th, and final repetition.

## Measured result

Release `-O3` WSL host, 2000 repetitions of the local 3936-byte capture,
with both VU1 banks explicitly cleared before each trial:

| Core | Timed VIF submit / VU pair-equivalent (two samples) |
| --- | ---: |
| `2197b90`, pre-optimization | 2286.13, 1679.09 ns |
| Optimized core | 75.05, 70.99 ns |

The conservative cross-sample comparison is roughly 22x faster; the wide old
range reflects host timing noise. The first version of this benchmark called
`Memory::zero` for VU banks, but that API only zeroes EE RAM and returned false.
These replacement measurements use the same corrected harness against both
commits. The timed interval is the entire `Vif1::submit`, including upload,
parsing, and VU execution. Bank clearing and checksum happen outside it.
This is a host throughput number, **not** VU-only speed or Vita frame rate.
The BIOS-derived capture stays local and is not committed.

A call-count profile of 5000 repetitions fell from about 4.77 million generic
`Memory::write32` calls in VIF submission to none in that path. Its total-time
percentages are dominated by the benchmark's untimed full-RAM checksums, so
they should not be mistaken for a VU-only cycle profile. Upper/lower arithmetic
dispatch is now the next interpreter cost worth measuring separately; guessed
math shortcuts would risk the unresolved clipping behavior.

To reproduce with an independently obtained VIF packet:

```sh
cmake --build build-release --target ps2vu_benchmark
./build-release/ps2vu_benchmark path/to/capture.bin 2000
./build-release/ps2vu_benchmark path/to/capture.bin 10000 --vu-first
```

The `--vu-first` mode discovers the first MSCAL from VIF run records, submits
the preceding commands to establish exact pre-run VU memory, and times only
`Vu1::run`. It restores written data words and resets VU state between trials;
periodic full-state/GIF checks compare against the VIF-driven first run. On
this capture that invocation is 55 pairs / 62 modeled cycles. With 10,000
repetitions, the separate old build measured 1795.76 ns per VU pair and the
optimized build 53.80 ns per pair, about 33x faster on the host. The state and
GIF hashes match exactly (`68FF21F4FF0A0BE0` and `488076C073542A10`). This
isolates one short prologue, not all 998 pairs or Vita hardware.

A canonical lower-NOP short-circuit was tried against the VU-only mode and
discarded: 53.62-59.29 ns/pair overlapped the existing 53.80 ns/pair result.
No speculative instruction or timing shortcut was kept without a measurable
gain and matching checksums.

Release CTest 14/14 and UBSan CTest 14/14 pass. A Vita VPK cross-build also
passes; no physical Vita runtime measurement is claimed. The benchmark's
checksum protects final state and GIF counters, while the existing per-lane,
same-pair, VIF provenance, XGKICK, and bank-edge tests guard intermediate
contracts. Remaining work: compare this exact VU input and flag decisions
against a trusted reference before changing clipping behavior. An offline VU
microprogram compiler is a later performance step; it must use this path as a
correctness fallback, not assume the present 998-pair run is visually correct.

## Why the full BIOS replay still reports 998 pairs

Added an opt-in VIF command census to `ps2bios_trace`, with an isolated unit
test. A bounded replay reached 300,000,000 EE steps before the 420-second host
deadline (`host_deadline=0`); the nonzero tool exit reflects the requested
step-limit endpoint, not an unsupported instruction. Local diagnostic output:
`build-release/vif-census-300m.txt`. No BIOS or packet data was committed.

The VIF1 frontend received 5362 nonempty packets totaling 4,064,912 bytes.
All VU run requests were in packet 1: one MSCAL and six MSCNT, accounting for
the known 998 pairs. The entire stream contained 5361 DIRECT commands, no
further MSCAL/MSCNT commands, no empty packets, and no rejected VIF commands.
There were also one MPG upload, seven UNPACK commands, and 56,293 NOP words.
Thus the later BIOS traffic takes VIF PATH2 toward
GIF/GS without starting VU1 again within this 300M-step window. The 998 count
is not an emulator execution ceiling or evidence of dropped later VU calls.

The endpoint (`PC=00272728`), GIF packet/draw counts, and framebuffer hash
`565638DCA404F0B3` match the earlier 300M replay, so this instrumentation
did not change observed rendering. It does not prove the first VU packet's
geometry or flag decisions are correct. For a recognizable intro, prioritize
reference-backed DIRECT/GIF/GS draw and display routing checks, while keeping
the first VU packet as a separate correctness question.

## Display routing boundary

An unchanged 300M-step replay with a read-only GS privileged-register dump
found `PMODE=0x66`: display circuit 1 disabled, circuit 2 enabled. Circuit 2
uses `DISPFB2=0x1450` (FBP 0x50, FBW 10, PSMCT32, source offsets 0,0) and
`DISPLAY2=0x001FF9FF01848290` (horizontal magnification 4, vertical
magnification 1, display rectangle 2560x512). Both `DISPFB` and `FRAME`
FBP fields use 8 KiB units: the selected FBP 0x50 has byte base `0xA0000`.
The exported 160x112 PPM is still a preview of the most recently bound draw
target, **not** a hardware-accurate display output; its final target address
is not logged. The bounded triangle records include a `FRAME` target with
FBP 0x50, but later target switches are possible.

Register offsets/field packing are documented by
[ps2dev gsKit](https://github.com/ps2dev/gsKit/blob/master/ee/gs/include/gsInit.h).
The FBP byte unit was cross-checked against
[PCSX2's `GSRegDISPFB::Block()`](https://github.com/PCSX2/pcsx2/blob/v2.8.2/pcsx2/GS/GSRegs.h),
which converts FBP to 256-byte block numbers by shifting left five. This
corrects an error in the first version of this checkpoint: a gsKit call-site
comment saying “Address/2048” was incorrectly treated as a byte unit despite
PCSX2's explicit block conversion. The previous `0x28000` probe, hash
`1E481BEAA3976189` and
14,911 nonblack RGB samples addressed the wrong page and are **invalid as
display evidence**.

The corrected 300M-step replay completed at the same `PC=00272728`, with
5,418 GIF packets, zero GIF packet rejections, 998 VU1 pairs, and unchanged
draw-target hash `565638DCA404F0B3`. The enabled circuit-2 linear probe now
uses byte base `0xA0000`, width 640, and has hash `377325F64EDED69D` with
7,536/17,920 nonblack RGB samples. Its picture contains the blue texture in
the upper part, while the draw-target preview contains the same texture in
the lower part. This is an address-origin difference, not a rendering change:
the RGB bytes of display-probe rows 0-47 exactly match draw-preview rows
64-111 (MD5 `ea9c1a6f6889eaa9bcebf4dc82755eb9` for each 160x48 crop).
The `0xA0000` base is exactly 256 native 640-pixel rows, or 64 rows on
Astra's quarter-resolution preview grid. The preview is therefore unsuitable
as a substitute for the enabled display circuit at this endpoint. This
overlap does **not** validate native GS scanout or establish that the image
matches PCSX2 at the equivalent BIOS instant.

The tracer can optionally save that linear display-page probe as a separate
PPM after `FIRST_VIF_BIN`, with `-` to skip the capture. This is deliberately
named a **linear probe**, not a finished display implementation: native GS
swizzling, interlace, output-circuit composition and exact sampling are not
modeled. A reference image or GS dump is needed before making the selected
page the Vita-facing framebuffer.

The earlier PPM export was correctly formed but sampled the wrong page. Its
visual difference from the draw-target preview was an artifact of that address
error, not evidence of a BIOS display-buffer mismatch. Corrected local outputs
are `build-release/display-corrected-300m.txt`,
`build-release/display-corrected-300m.ppm`, and
`build-release/display-corrected-linear-300m.ppm`; they are ignored and not
committed. Release and UBSan CTest remain 14/14. The next correctness gate is
a small reference-backed display-buffer switching fixture and comparison of
the PATH2 GS draw stream; do not choose a Vita-facing framebuffer from this
linear approximation alone.
