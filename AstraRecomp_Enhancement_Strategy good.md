# AstraRecomp — Enhancement Strategy

**Prepared as an external technical review · 2026-08-30**
**Scope: ideas to enhance the repo, honest pros/cons, con-mitigation plans, and the tricky problems ahead**

Everything below is grounded in the actual repository state (commit `985f67f`, "Run BIOS SIF handshake entirely in guest code"), which was independently cloned, built with `g++ -Wall` (clean), and whose full host test suite (28 test groups, 167 assertions) passes.

## 1. Verified starting point

| Asset | Status |
| --- | --- |
| Portable C++17 core (`ps2core`, no Vita headers) | ~5,250 LOC total, compiles clean, tests pass |
| EE interpreter | ~128 instruction variants, 128-bit GPR state, delay slots, COP0/COP1 basics, early MMI |

The honest one-line summary: **a methodologically correct, tiny slice of an enormous machine.** The strategy below is about widening that slice in the order that buys the most, without breaking the project's greatest asset — the interpreter-as-oracle discipline.

---

## 2. Pros — what you have that most hobby emulators never get

1. **Oracle-first methodology.** Interpreter is architectural truth; AOT is validated against it. This is the single strongest thing in the repo. It is also your best defense against the biggest risk of AI-assisted development velocity (see Cons).
2. **Honest scoping.** README and ROADMAP explicitly say "does not run games yet" and "first targets should be homebrew and simple 2D titles." Underclaiming is a strategic asset: it builds credibility and keeps motivation attached to real milestones.
3. **Determinism as a design property.** Deterministic generator output, package validation, bounded slices, exact-PC fallback. Determinism makes bugs reproducible, enables trace-diffing, save states, and rewind almost for free later.
4. **Clean boundary architecture.** Portable core / Vita frontend split means you can run ASan/UBSan/fuzzers on a PC before risking Vita crashes. Most Vita homebrew projects die on hard-to-debug device crashes.
5. **LLE IOP foundation.** You already execute the real IOP reset ROM instead of faking the boot handshake. That is strategically important: retail games load their IOP modules from disc, and an R3000A interpreter that already works turns "run the game's IOP" from an HLE cliff into an incremental path.
6. **Vita3K as a dev loop.** You can iterate on VPKs without hardware transfer — a velocity multiplier that PS2-on-X project teams in the 2000s would have killed for.
7. **Session handoff docs.** The SESSION_*.md files are excellent continuity practice for a solo/small team. They should graduate into GitHub Issues (see §7).

**Rule: protect #1–#3 at all costs.** Every performance idea below is designed so the deterministic oracle path stays alive as a build flag.

## 4. Performance budget reality (the math that should drive decisions)

Fermi estimates, stated assumptions, no false precision:

- **EE guest work**: 294.912 MHz, sustained IPC in real code ≈ 0.5–1.0 (dual-issue peaks don't last) → **~150–300M guest instructions/sec** in busy scenes.
- **One Vita A9 core @ 444 MHz**: sustained ≈ 400–800M host instructions/sec (out-of-order, ~1–1.8 effective IPC for tight code).
- **Translation expansion**: interpreter-shaped C++ is 6–15 host instructions per guest op. That's the fail case: ~10x expansion → you can afford ~1/10 of EE speed. **The whole performance question is: how low can you push expansion?**
  - Current generated code (measured from `phase0_aot_package.cpp`): every instruction reloads `state.gpr[n]`, writes `state.pc`, and branches — realistically 8–15 host instructions per guest op.
  - With **local promotion + deferred writeback** (§5, item 8): hot registers live in C++ locals (→ ARM registers), PC only at exits → ~3–5 host ops per guest op.
  - With **memory fast paths** (item 9) and **block linking / return prediction** (item 10): dispatch overhead approaches zero.
  - At ~3x expansion, one A9 core ≈ EE throughput for scalar code — *borderline but real*, before spending cores 2–3.
- **GS**: absolutely must go to the GPU (GXM). Software GS is the oracle at 160×112 only. 4 MB GS local memory as a texture atlas is trivial in the Vita's 128 MB VRAM.
- **SPU2**: 48 voices × 48 kHz ≈ 2.3M samples/s; scalar decode ≈ 25–45 MIPS (a tenth of a core!) → **NEON ADPCM decode is mandatory**, not an optimization (§5, item 18).
- **Threading layout**: core 0 = EE (+VU0 macro), core 1 = GIF/GS feed + presentation, core 2 = SPU2 + IOP + file I/O. The deterministic single-thread mode stays as a build flag for debugging and TAS-grade determinism.

**Conclusion the numbers support:** homebrew and 2D titles are comfortably in budget; light 3D (early-era, VU1-light) is the stretch goal; demanding late-era 3D is out of reach on this hardware — say so publicly and nobody can accuse you of overpromising.

## 5. Ranked idea backlog

### Tier 1 — correctness & velocity (do these first, they're cheap and multiply everything)

1. **Opcode frequency profiler.** Add an interpreter mode that histograms executed opcodes (per milestone phase: ELF boot, BIOS stage 1, stage 2…). One day of work. From then on, every generator-expansion decision is data-driven ("the next 30 opcodes cover 97% of dynamic instructions in the BIOS") instead of guesswork. Publish the histograms in `docs/` — they're also great devlog material.
2. **Differential fuzzing harness.** You already have seeded differential coverage; generalize it: generate random guest programs from the *supported* opcode set (plus small amounts of unsupported ones), run interpreter vs AOT, assert identical final state (regs, memory, cycles, PC, stop reason). Add to CI with a fixed seed corpus. This mechanically catches generator regressions for the rest of the project's life.
3. **CI matrix (GitHub Actions).** Jobs: gcc + clang host builds, ASan+UBSan test run, generator determinism (build twice, byte-compare), VitaSDK cross-build, Vita3K scripted VPK boot with screenshot artifact. The repo is already deterministic-build-friendly, so this is nearly free.
4. **Scheduler event deadlines.** Today `run_slice` interleaves IOP at a fixed 1:8 ratio with no event deadline. Add an event queue (timer fire, DMA completion, SIF flags) and **cap each EE run to the next event deadline**. Without this, a game that arms a timer and spin-waits will see it fire arbitrarily late — one of the classic "works in my emulator, hangs on hardware" bugs. (§6, T2.)
5. **Compiler hygiene for COP1 determinism.** Add `-ffp-contract=off` (and never `-ffast-math`) to the core target; write bit-exact COP1 tests. Clang may otherwise fuse `mul.s`+`add.s` into FMA and silently break PS2 float semantics — a bug class that's invisible until a game's physics drifts. Then implement the R5900 FPU quirk layer (no NaN/Inf generation, flush-to-zero) as an explicit function layer, per your own ARCHITECTURE.md TODO.
6. **BIOS progress KPI + golden checkpoints.** Record (cycles, PC, key regs) hashes at fixed BIOS milestones (ROM entry, RAM clear done, IOP reset, SIF init, Initialize Done). Two payoffs: instant regression detection ("which milestone broke?") and a performance KPI ("cycles to Initialize Done" must not regress). Track both numbers per commit.
7. **Rich fault dumps.** Extend `fault.txt` with a ring buffer of the last N block PCs (and last IOP PCs). Turns "it stopped at 0x..." into "here's the last 64 blocks" — the single biggest bug-triage accelerator for a project whose test loop involves a real console.

### Tier 2 — performance & graphics (the next milestones)

8. **Local promotion + deferred writeback in the generator.** The highest-leverage AOT change available. Current output per instruction: read `state.gpr[x]`, compute, write `state.gpr[x]`, write `state.pc`. Instead: the generator already knows each basic block; do a (simple, within-block) liveness pass and keep hot GPRs in C++ locals, writing back only at block exit and on calls/memory faults. The host compiler then keeps them in real ARM registers. Expected: roughly halves host instructions per guest op. Ready-to-paste example in §7.2.
9. **Memory fast path in generated code.** Emit an inline check for the flat-RAM case (single compare + mask for KSEG aliases), call the full `Memory` helper only for TLB/MMIO/unaligned/cross-page. Guard self-modifying code with **page-version stamps**: a per-page generation counter checked once at block entry; if a store inside the block bumped the version, exit to the dispatcher (which re-validates). This is the standard recompiler answer to SMC without giving up fast paths.
10. **Block linking + return prediction.** AOT functions can't be patched at runtime, but the dispatcher can: keep a small direct-mapped per-PC "last target" table (function-pointer cache). On `jr $ra`, look up `ra`; on hit, call directly — no table walk, no hash. On miss, fall back to `find_aot_function`. Also emit direct `goto` chains for statically known direct edges inside one function (you already do this for JAL/T1; extend to all direct branch edges at the package level).
11. **NEON MMI mapping.** Map the 128-bit GPR file to `uint32x4_t`. Most of the hot MMI family maps 1:1: `PADDW`→`vaddq_u32`, `PADDSW`→`vqaddq_s16`, `PSUB*` similarly, `PEXTW`→shuffle, `POR/PAND/PXOR`→bitwise. The ugly ones (`QFSRV`, `PVAL`, `PCPY*`, `PMFHI/LO` lanes) stay interpreter-first — but only the frequency profiler (item 1) should decide which of those are worth native paths. Keep the interpreter as the lane/saturation/flag oracle, exactly as ARCHITECTURE.md already prescribes.
12. **GXM GS backend plan (there is no Vulkan on Vita — plan for GXM or vitaGL).**
    - Keep the 160×112 software rasterizer forever as the **GS oracle** (diff its output against the GPU backend in tests — mirrors the CPU oracle philosophy, same project DNA).
    - GS local memory (4 MB) lives as a host texture atlas; render targets are sub-rects.
    - CLUT textures: index texture → 256-entry palette texture → two dependent point samples in the fragment shader (the standard palette-in-shader approach).
    - Alpha test / TEXA / PABE / alpha-fail modes: fragment-shader `discard` permutations, cached per GS register configuration.
    - **Texture cache with page-dirty tracking** — the part that actually makes games render (detect when a game reuses a framebuffer region as a texture; alias the same host texture instead of re-uploading).
    - Explicit descope list: scanmask, PS2 dither (optional later), exotic interlace handling (bob only), per-pixel reads outside readback paths. **Policy: 1× native resolution, single upscale to 960×544. Never chase upscaling** — the budget goes to compatibility, not pixels.
13. **Threading layout (epoch model).** Core 0 EE, core 1 GS feed/present, core 2 SPU/IOP/IO. Keep determinism debuggable by making threaded mode interleave at fixed epochs (e.g., EE advances 25k instructions → GS queue drains fully → repeat). Not cycle-perfect, but reproducible — and the single-thread build remains the perfect oracle. Threading only *after* the single-threaded path runs a flagship title correctly (per your own roadmap M6 ordering — it's the right order).
14. **Audio-paced timing.** Drive the emulation slice cadence from `sceAudioOut` buffer consumption instead of vsync — the classic handheld-emulator trick that eliminates frame-pacing jitter and couples game speed to wall time through the audio clock. Present on vsync separately.

### Tier 3 — strategic bets

15. **Per-title AOT packaging pipeline (the "product" form factor).** A Vita can't run a Python generator at runtime, so the realistic architecture is: PC-side tool builds an AOT package for a specific title's known modules → ships inside the VPK alongside the interpreter → interpreter handles everything the package doesn't cover (dynamic overlays, self-modifying code, anything cold). **Design the package format for this now** (module identity, ranges, per-module fingerprints) — you already have the ABI/fingerprint validation to build on. This is also the honest answer to "why static recomp on a machine that can't JIT user code": *precompile on PC, interpret the rest.*
16. **Save states / rewind / fast-forward.** Your determinism-first design makes these nearly free: serialize Memory (32 MB EE + 2 MB IOP) + CPU/IOP/GS state, compress (guest RAM is mostly zeros and repeated patterns — LZ4 will crush it), ring-buffer ~30 states for rewind. On a handheld, savestates are the single most loved emulator feature; as a demo of "determinism pays rent," they're unbeatable.
17. **IOP continuation + device HLE.** LLE the IOP modules games load from disc (you own the interpreter), HLE only the physical devices: CDVD state machine (with *approximate* seek/rotational latency — some games poll drive status and hang on instant responses), sio2 (pads), memory cards (file-backed 8 MB images). See T9.
18. **SPU2 with NEON ADPCM.** Voices decode via NEON (interleave 4 voices per `q` register), simple linear interpolation, skip reverb initially, mix to the Vita audio out. Budget check in §4 says this is mandatory-NEON territory.
19. **Flagship title program.** Pick: (a) one PS2 homebrew game **with available source** — gold, because you can compare against the real thing and even build a native-Vita reference build; and (b) one simple 2D commercial-era title as the distant target. Every milestone from M3 onward gets its acceptance test defined by the flagship. This single decision does more against C1 (scope drift) than any process fix.
20. **Community positioning.** "PS2-on-Vita research platform" with: the opcode histograms (item 1), the BIOS progress KPI graphs (item 6), devlog posts per milestone, and monitor VPK releases. The Vita scene amplifies honest, verifiable progress; the emulation scene amplifies oracle-first methodology. Do not market it as "PS2 games on Vita."
21. **(Conditional) VU0-macro AOT via NEON.** VU0 macro mode is statically in the instruction stream, so it recompiles like MMI (item 11). VU1 microcode JIT stays parked until a 3D flagship exists that justifies it — building a VU1 JIT without a target is how projects stall.

## 6. The tricky problems — deep dives

These are the parts that will actually hurt. Each gets: why it's hard, the technique, and the escape hatch.

**T1. Self-modifying code & runtime-loaded overlays.**
Why hard: games overwrite their own code (overlay loaders, decompression stubs, trampolines). AOT packages are precompiled; SMC invalidates them at runtime.
Technique: page-version guards at block entry (§5, item 9) for correctness; per-module AOT packages keyed on module fingerprint for coverage.
Escape hatch: interpreter fallback at exact PC — you already have it. Overlays simply run interpreted until the PC-side tool learns that module.

**T2. Interrupt latency and event quantum.**
Why hard: your scheduler runs bounded slices with a fixed 1:8 EE/IOP interleave. A timer or DMA completion that becomes due mid-slice fires late; delay loops calibrated on real hardware then misbehave.
Technique: event queue with deadlines; cap `cpu_.run()` to `min(remaining, next_event - now)`; deliver events at exact cycle counts.
Escape hatch: shrink slice size at correctness cost of responsiveness — fine for the oracle build, unacceptable for the fast path, so do it properly early.

**T3. FPU semantics vs the host compiler.**
Why hard: R5900 FPU has no NaN/Inf generation, flushes denormals, and your ARCHITECTURE.md honestly notes COP1 currently uses host IEEE floats. Meanwhile the host compiler *wants* to fuse multiplies and adds.
Technique: `-ffp-contract=off` today; an explicit `ps2_float`-style operation layer (the one good idea worth salvaging from the strategy doc that circulated); bit-exact COP1 test vectors; compare against PCSX2 (§5, item 4 of Tier 1 / C4).
Escape hatch: until conformance work lands, keep COP1 in the interpreter path only (AOT packages already fall back per-opcode).

**T4. Division: MIPS has it, Cortex-A9 doesn't.**
Why hard: Cortex-A9 has **no integer divide instruction**. Every guest `DIV` becomes a call to `__aeabi_idiv` (~20–40 cycles). Compilers emit DIV more than you'd hope.
Technique: strength-reduce in the generator (constant divisor → multiply-shift; power-of-two → shift); keep everything else on the helper; the frequency profiler tells you if a per-site cache is ever worth it.
Escape hatch: none needed — it's bounded cost — but decide the DIV-by-zero convention once (architecturally UNPREDICTABLE; pick the hardware-observed values) and match the interpreter bit-exactly.

**T5. GIF PATH arbitration and MFIFO.**
Why hard: GIF is fed from three sources (PATH1: VU1 direct, PATH2: EE GIF registers, PATH3: DMAC) with arbitration rules, plus MFIFO ring-buffer DMA mode that some games use to feed the GIF through SPR. Getting priority/stall semantics wrong = corrupted geometry that "mostly looks fine."
Technique: serialize all three paths through one FIFO in the deterministic build (correctness first), then measure before parallelizing. Implement MFIFO as a DMAC mode, not a GIF special case.
Escape hatch: descope MFIFO titles until a flagship needs it — it's rare in 2D-era code.

**T6. GS readback, texture aliasing, and interlace.**
Why hard: games read framebuffers back to EE memory, render to textures, and use FIELD-interlaced modes. The Vita panel is progressive.
Technique: texture cache with dirty-page tracking (§5, item 12); implement readback paths explicitly (slow but correct); bob deinterlace only, document weave/bob artifacts per title.
Escape hatch: readback-heavy effects get a per-title override list — your `ps2_game_overrides`-style hooks belong in the runtime eventually.

**T7. Cache coherency games.**
Why hard: the EE cache-isolation bit (`Status.Isc`) during BIOS code patching is already handled; but some games do DMA on memory that's still dirty in D-cache, or rely on scratchpad/DMA timing.
Technique: keep emulating caches only to the extent titles observe them (Isc toggles, cache ops); don't model full cache hierarchies — nothing good comes of that for performance.
Escape hatch: your null-bus/strict-stop discipline ("invalid ops stop deterministically") is the right default; extend it to coherency surprises.

**T8. Clock domains and drift.**
Why hard: EE 294.912 MHz, IOP 33.8688 MHz (your 1:8 ratio ≈ hardware), SPU2 on its own buses, GS presentation at 50/60 Hz. Naive per-slice stepping accumulates drift → games with vsync-calibrated loops jitter.
Technique: one master clock in cycles; derive all domains from it; audio-paced wall-time coupling (§5, item 14).
Escape hatch: none — this is load-bearing. But your "COP0 Count driven by interpreted EE cycles" foundation is the right shape to build it on.

**T9. IOP module loading (the real fork in the road).**
Why hard: retail boot replaces IOP modules from disc (IOPRP images, some packed) before the game's EE code even starts. Pure HLE (PCSX2-style) skips this; pure LLE must execute it *and* emulate the devices those modules drive (CDVD, sio2, memcards).
Technique (recommended): **LLE IOP + HLE devices** — execute the modules with your R3000A interpreter, HLE the physical devices at the register level. Reuses your existing investment, avoids per-game HLE quirk chasing, matches your LLE-first DNA.
Escape hatch: none, but staged — M2→M5 in your roadmap already walks this path in the right order.

**T10. Threading vs determinism.**
Why hard: the performance budget (§4) requires 3 cores, but naive threading destroys reproducibility and reintroduces the race-class bugs your design currently excludes.
Technique: epoch model (§5, item 13) — fixed interleaving quanta, single-writer queues, no shared mutable guest state without ownership transfer.
Escape hatch: single-threaded debug build forever, as oracle and for bug reports ("reproducible in deterministic mode" is a support superpower).

**T11. Vita3K fidelity gaps.**
Why hard: Vita3K is a moving target with its own timing/GPU inaccuracies; a pass in Vita3K is necessary, not sufficient.
Technique: CI smoke test in Vita3K for structural regressions; hardware soak script (C8) for the truth; treat any Vita3K-only failure as *its* bug until proven otherwise.
Escape hatch: none — just always run both.

**T12. I-cache pressure from AOT packages.**
Why hard: a full game's AOT package is tens of MB of ARM code against a 32 KB/core I-cache; cold code thrashes.
Technique: order functions by measured hotness; align hot entries; keep the interpreter hot-loop compact; profile on hardware, not Vita3K.
Escape hatch: interpreter fallback means cold code costs speed, never correctness.

**T13. BIOS version variance.**
Why hard: you validate against one dump; different BIOS revisions have different timing assumptions and code paths.
Technique: golden checkpoint hashes (§5, item 6) per BIOS revision in your test matrix; accept "known-good revisions" list rather than chasing all.
Escape hatch: document the validated revision(s) and treat others as best-effort.

**T14. SPU2 IRQ/DMA timing.**
Why hard: some games sync their audio engines to SPU2 interrupts and DMA half-transfer events; wrong timing = hangs, not just bad sound.
Technique: implement SPU2 IRQ as a first-class event-queue citizen (T2's event system), not a side effect of mixing.
Escape hatch: per-title overrides to disable IRQ-dependent paths.

### 7.2 Local promotion — before/after (using the repo's own generated code)

Today (`generated_00003000`, per instruction):

```cpp
state.pc = 0x00003004u;
state.gpr[4] = sign_extend_32(static_cast<std::uint32_t>(state.gpr[0]) + 40u);
++executed;
```

With within-block promotion (r4 and r0 are block-live; pc is written once):

```cpp
// entry: u32 r0 = u32(state.gpr[0]);  u32 r4 = u32(state.gpr[4]);
r4 = r0 + 40u;                 // stays in an ARM register
++executed;
// exit: state.gpr[4] = sign_extend_32(r4);  state.pc = 0x0000300Cu;
```

The generator already has the block tables; this is a within-block liveness pass (GPRs are dead at block boundaries, spill on every exit contract you already emit). Expected host-instruction reduction: ~2x on scalar code — the single biggest AOT win available to you.

### 7.3 Return prediction in the dispatcher

```cpp
// Direct-mapped, 512-entry, indexed by (pc >> 2) & 511.
// Written by the dispatcher on every successful lookup.
static AotFunctionEntry* last_target[512];

inline AotExit run_aot(const AotPackage& pkg, Memory& m, CpuState& s) {
  auto*& slot = last_target[(s.pc >> 2) & 511];
  if (slot && slot->function && slot->contains(s.pc)) {   // one compare
    const AotExit e = slot->function(m, s);
    if (e.kind != AotExitKind::Interpreter) return e;
  }
  slot = const_cast<AotFunctionEntry*>(find_aot_function(pkg, s.pc));  // miss path
  ...
}
```

### 7.4 Page-version SMC guard (block entry, emitted by the generator)

```cpp
// one load + compare at function entry; store path bumps the version
const u32 ver = memory.page_version(entry_page);
... run block ...
if (memory.page_version(entry_page) != ver)   // checked at exits that stored
  return {AotExitKind::Interpreter, StopReason::None, state.pc, executed};
```

## 9. Anti-goals — things that would sink this project

1. **No Vulkan/DirectX anything.** The Vita has neither. GXM/vitaGL is the only lane (this is why the circulating "strategic blueprint" doc missed the project).
2. **No upscaling chase.** 1× native, one upscale, budget goes to compatibility.
3. **No LLVM IR rewrite now.** Maybe someday for the PC tool; today it's a two-quarter detour for a generator that hasn't finished its first opcode family.
4. **No VU1 JIT before a 3D flagship exists.** Building it speculatively is the classic stall.
5. **Don't replace the interpreter — ever.** It's the oracle, the BIOS path, the fallback, and the debugger. Every "optimization" that deletes the oracle deletes the project's soul.
6. **No per-game HLE hacks before M5.** One `ret0` too many and you're maintaining a lie.
7. **No retail-compatibility marketing.** The moment the story outruns the code, credibility — your main asset — is spent.
